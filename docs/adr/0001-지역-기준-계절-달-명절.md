# 0001. 지역 기준: 계절은 방문자, 달·명절은 한국
- 상태: 채택
- 날짜: 2026-10-15 (달은 2026-10-12) · 기록: 2026-10-24
- 출처: `TIME_BASE_PLAN.md` 3·4장, `MOON_PLAN.md` 6장, `WINDOW_PLAN_3.md` 2장·4-1, `CLOCK_PLAN.md` 11장(처음 나온 질문)

## 맥락
- 방은 한국 고양시 아파트지만, 보는 사람은 어디서나 본다(만든 사람부터 시드니).
- 기기 시간대가 남반구면 `season()`이 계절을 뒤집고 있었다. 시드니 기기에선 10월이 봄. 반면 달은 한국 기준으로 고정했다(MOON_PLAN). 계절도 한국에 맞출지 정해야 했다(CLOCK_PLAN 11장).
- 창밖 풍경(산·단풍·벚꽃·철새)이 늘면서 이 기준이 화면 전체에 번진다.

## 결정
- **계절은 방문자 지역 기준.** 남반구 시간대면 뒤집는다. 창밖 풍경은 "풍경 날짜"로 읽는데, 남반구에선 `yearPos`가 반년(0.5)을 밀어 준다 → 시드니 10월 = 한국 4월 풍경.
- **달은 한국 기준 고정.** 차오르는 달은 어디서 보든 오른쪽이 빛난다(창밖은 한국 하늘). 위치 권한도 필요 없다.
- **명절·기념일은 한국 달력**(할로윈·크리스마스 포함). 날짜는 방문자 기기 날짜.
- 한곳에서 바꾼다: `time.js` `REGION = { season: 'local', moon: 'korea', holidays: 'korea' }`. 시간대 판단 `SOUTH`는 `REGION`을 거쳐서만 쓴다(`seasonSouth()`, `MOON_SOUTH`).

## 결과
- 보는 사람의 창밖 계절이 자기 바깥 날씨와 맞는다. 대신 남반구에선 "한국 아파트 창밖이 봄인데 달력은 할로윈" 같은 어긋남이 생기고, 이를 받아들인다.
- 계절과 달이 서로 다른 기준이라는 점을 기억해야 한다(달은 `REGION.moon`, 계절은 `REGION.season`).
- 기준을 바꾸고 싶으면 `REGION` 값 하나만 고친다. 검사는 `check_time.mjs`를 `TZ=Australia/Sydney`·`TZ=Asia/Seoul` 두 프로세스로 돌려 확인한다.
- 관련: 0002(해 시각도 풍경 날짜를 따른다).
